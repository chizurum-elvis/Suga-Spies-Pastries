# Failed delivery and redelivery

The owner marks a genuine failed first delivery attempt on the order page and records whether the cause was the customer/address or the business. The order remains paid but moves to `delivery_failed`. The customer receives an order-link email and has **24 elapsed hours** from the failed-at instant to confirm or correct the delivery address. The address is validated through the existing Google Maps server integration; the business's configured GTA area and maximum distance still apply. The original paid order and address remain immutable audit history.

After the customer responds, the owner chooses an open date. This redelivery occupies one of the same four daily capacity spaces as new orders. The original free-delivery threshold remains free on redelivery, as does a business-caused failure. Otherwise, the current distance-based delivery fee is quoted for the corrected address. A paid date remains provisional until the customer completes a separate CAD Stripe card/Apple Pay/Google Pay checkout. Starting fee payment reserves the space for 15 minutes. Stripe verification, not the browser return URL, confirms the new date. Link and automatic tax are disabled for this fee checkout; the existing no-tax business decision is unchanged.

If the customer does not respond in 24 hours, the worker closes the order and queues a full refund of the original payment. If the second delivery attempt fails, the owner closes the order, releases the redelivery capacity space, and queues a full original-payment refund plus a refund of any additional paid redelivery fee. A late fee payment is refunded first, then the original order is closed and refunded. All refund jobs are durable and independently tracked in the admin order view. Provider ambiguity is surfaced for owner review; the application never declares a refund complete before Stripe confirms it.

## Deployment and worker

1. The linked database has `20260929150250_failed_delivery_redelivery.sql` and the two same-day compatibility migrations applied after the cancellation/refund migration. On a fresh database, apply them in filename order. `npm run test:db:redelivery:migration` is a **pre-application** rollback test; after the migrations are applied, use `npm run test:db` instead.
2. Existing Stripe, Google Maps, Resend, Supabase, order-access, and worker secrets remain required. This feature adds no new secret.
3. Keep the authenticated reconciliation worker running at least once a minute. The repository's daily Vercel Hobby cron is **not sufficient** to honor a 24-hour response deadline promptly or release a 15-minute fee hold. Use a per-minute Vercel schedule on a suitable plan or another authenticated scheduler calling `POST /api/internal/payments/reconcile` with `Authorization: Bearer <PAYMENT_WORKER_SECRET>`. Locally, run `npm run payments:worker` in a separate terminal. Monitor worker health and owner refund-attention alerts.

## Sandbox acceptance walkthrough

Use only sandbox Stripe keys and test orders. Place a paid test order, then in `/admin/orders/[id]` advance it through preparing, ready, and out for delivery. Mark the first attempt failed. Open the customer order link from the test email; confirm or correct the address before its displayed deadline. Verify the owner sees the corrected address and selects an open date. Check that free-original-delivery and business-fault examples schedule without a new payment, while a customer/address failure after paid original delivery requests only the additional fee. Complete the fee with a Stripe test card and confirm the new date appears only after reconciliation. **On the selected Toronto delivery date**, mark the order out for redelivery, then delivered. In another sandbox order, mark the second attempt failed and verify both relevant refund records and terminal order status. Use the rollback-only SQL test for deadline, fifth-slot, late-charge, and race-sensitive cases rather than changing a real order's clock.

The site is not ready for live redelivery until an actual test email, address check, Stripe fee payment, webhook/worker reconciliation, and both refund paths have been observed end-to-end in the deployed environment.
